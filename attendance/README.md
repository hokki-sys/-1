# 출퇴근 관리 (온라인)

매장 여러 곳을 운영하는 소규모 사업장을 위한 RFID 출퇴근 관리 시스템입니다.
데스크톱 단일 파일 프로그램(v6.17)을 온라인으로 옮기면서 설계를 다시 짰습니다.

**설계의 축: 네트워크가 죽어도 카드는 찍혀야 합니다.**
통신 장애 때 출근이 한 번이라도 실패하면 직원들은 그날로 종이에 적기 시작하고,
시스템은 신뢰를 잃습니다. 그래서 매장 단말은 인터넷 없이 완결되는 동작만 맡고
(태그 읽기 → 로컬 저장 → 즉시 응답), 클라우드는 진실의 원천과 판단을 맡습니다.

```
매장 (인터넷 없이도 완결)              클라우드 (진실의 원천)
카드 태그                              수집 API (멱등)
   ↓ UID                                  ↓ 그대로 저장
엣지 에이전트 ──→ 화면 즉시 응답        원본 탭 이벤트 (불변)
   ↓ 먼저 적재                             ↓ 규칙으로 짝 맞춤
로컬 큐 (SQLite) ┄┄┄복구 시 일괄 전송┄┄→ 근무 세션 (파생, 재계산 가능)
                                          ↓
                                      웹 관리자 · 근무표 · 리포트
```

## 핵심 설계

| | 무엇을 | 왜 |
|---|---|---|
| **D1** | 단말은 판정하지 않고 수집만 | 오프라인이면 직전 기록을 알 수 없습니다. 판정을 서버로 미루면 문제가 사라지고, 규칙을 고치면 **과거 데이터도 다시 계산**됩니다 |
| **D2** | 출퇴근 시각 = 단말이 찍은 시각 | 큐에 3시간 있다 올라온 이벤트를 도착 시각으로 찍으면 급여가 3시간 틀립니다. `received_at` 은 감사용으로 따로 남깁니다 |
| **D3** | 달력 날짜 대신 **영업일** | 새벽 1시 퇴근은 전날 근무입니다. 컷오프(기본 05:00)를 데이터 모델에 넣어 자정 문제를 없앱니다 |
| **D4** | 매장마다 스키마 분리 | 요청 진입부에서 `search_path` 를 고정하므로 쿼리에 `store_id` 를 쓸 일이 없습니다 — **빠뜨려서 남의 데이터가 새는 사고가 성립하지 않습니다** |
| **D5** | 카드 유지 (폰 출퇴근 아님) | 주방은 손이 젖어 있고 폰이 없습니다. 카드 UID 는 생체정보가 아니라 규제 부담도 가볍습니다 |
| **D6** | 알림은 서버에서 비동기 | 알림 실패가 출퇴근 기록을 막으면 안 됩니다 |
| **D7** | OCR 은 인터페이스 뒤에 | 비전 모델이 실험 단계라 설정으로 갈아끼웁니다. 사진은 조각내 보냅니다 |
| **D8** | 근무표는 앱에서 작성 | OCR 은 온보딩용으로 내려갑니다. 발행된 근무표만 지각 판정의 기준입니다 |

## 빠른 시작

```bash
# 1) PostgreSQL 준비 (스키마 분리가 설계의 핵심이라 SQLite 로는 안 됩니다)
createdb attendance

# 2) 설정
cp .env.example .env      # DATABASE_URL, SECRET_KEY 를 채우세요
pip install -r requirements.txt

# 3) 공용 스키마 + 첫 매장
python3 tools/migrate.py
python3 tools/provision_store.py --slug gangnam --name "강남점" \
    --owner-email owner@example.com --owner-name "사장님" --owner-password "..."

# 4) 실행
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

`/s/gangnam/` 으로 접속합니다. 화면을 실제 모양으로 보려면:

```bash
python3 tools/seed_demo.py --slug gangnam    # 직원 6명 + 2주치 기록 + 근무표
```

### 매장 추가

```bash
python3 tools/provision_store.py --slug hongdae --name "홍대점" \
    --owner-email owner@example.com --owner-password "..."   # 같은 계정에 매장만 추가
```

계정은 공용이므로 한 번 로그인하면 상단에서 매장을 전환합니다.
매장이 늘면 마이그레이션도 매장 수만큼 돌아갑니다:

```bash
python3 tools/migrate.py --status    # 매장별 스키마 버전 확인
python3 tools/migrate.py             # 전부 최신으로
```

### 매장 단말

관리자 화면 → **단말** 에서 토큰을 발급합니다. **발급 시 한 번만 보입니다.**

```bash
cd edge
cp agent.ini.example agent.ini      # base_url, token 을 채우세요
python3 agent.py                     # 시리얼 리더기
python3 agent.py --stdin             # 리더기 없이 테스트
```

에이전트는 표준 라이브러리만 씁니다(시리얼 리더기를 쓸 때만 `pyserial`).
인터넷이 끊겨도 카드는 찍히고, 복구되면 큐가 자동으로 올라갑니다.

### 근무표 가져오기 (선택)

`.env` 에 `DEEPSEEK_API_KEY` 를 넣으면 사진에서 근무표를 읽어옵니다.
사진은 자동으로 조각내 보냅니다 — 통째로 보내면 서비스 쪽에서 약 800×800 으로
축소돼 글자가 뭉개지기 때문입니다.

> **먼저 확인하세요.** 근무표 사진에는 직원 이름이 들어 있고 인식을 위해 해외로
> 전송됩니다. 개인정보 국외이전에 해당할 수 있습니다. 그래서 서버 키와 별개로
> **매장별 스위치**(`ocr_import_enabled`)가 기본 꺼짐입니다. 직원 고지·동의를
> 받은 뒤 켜세요. 켜지 않아도 근무표 편집기는 그대로 씁니다.

## 테스트

```bash
pytest                      # 113개
pytest tests/test_domain.py # DB 없이 도는 순수 로직만
```

통합 테스트는 진짜 PostgreSQL 에 붙습니다. 스키마 분리가 설계의 핵심이라
SQLite 로 흉내 내면 검증이 안 됩니다. 테스트 전용 매장 두 곳을 만들고 끝나면 지웁니다.

## 구조

```
app/
  domain/          DB 를 모르는 순수 로직 — 여기가 급여 숫자의 출처입니다
    sessions.py      탭 → 근무 세션 (짝 맞추기, 중복 태그, 퇴근 누락)
    business_day.py  영업일 경계
    workhours.py     반올림, 지각 판정 (한 벌만 존재)
    schedule.py      근무표 합계와 경고
  models/          control.py(공용) · store.py(매장별)
  services/        수집, 재계산, 근무표, 리포트, OCR
  routers/         화면과 API
  db.py            매장별 search_path 라우팅
edge/agent.py      매장 단말 (오프라인 큐)
tools/             마이그레이션 · 매장 생성 · 데모 데이터
```

### 데이터가 어디 있나

| 공용 (`control` 스키마) | 매장 (`store_<slug>` 스키마) |
|---|---|
| `stores` `users` `user_store_roles` `devices` | `employees` `punch_events` `work_sessions` `adjustments` `schedule_weeks` `schedule_entries` `shift_presets` `schedule_revisions` `schedule_imports` `audit_logs` |

**계정을 매장 안에 넣지 않습니다.** 두 매장을 겸하는 점장이 계정을 두 개 갖게 되고
사장님은 매장 수만큼 로그인해야 하기 때문입니다. 사람은 공용, 데이터는 매장별.

## 데스크톱 버전에서 고친 것

앞선 코드 감사에서 나온 항목들입니다.

- **F-05 자정 넘김** — 날짜로 찾지 않고 이벤트 스트림으로 잇습니다
- **F-06 중복 태그** — 최소 간격 안의 재태그는 무시하고 원본은 남깁니다
- **F-11 하루 2탕** — 하루에 여러 근무를 허용합니다 (`10-14 17-22`)
- **F-12 이름 매칭** — 미등록 이름은 조용히 누락되지 않고 보고됩니다
- **F-14 인원 중복 카운트** — 행이 아니라 사람 수를 셉니다
- **F-15 동명이인** — 집계 키가 전부 `employee_id` 입니다
- **F-16 기록 삭제** — 퇴사는 소프트 삭제, 근무 기록은 보존됩니다
- **F-18 반올림** — 단위와 대상이 설정으로 나와 있고 화면 표기와 일치합니다
- **F-24 마이그레이션** — Alembic, 매장별 버전 관리
- **F-26 지각 판정 중복** — `is_late()` 한 벌만 존재합니다

원본 탭은 **절대 수정하지 않습니다.** 관리자 보정은 `adjustments` 에 사유와 함께
쌓이고, 해당 세션에는 표시가 붙어 재계산이 덮어쓰지 않습니다.

## MVP 에 아직 없는 것

- 알림 발송 (웹푸시·이메일·알림톡) — 인터페이스만 있고 구현은 다음 단계
- 직원 본인 로그인 화면 (역할과 권한은 이미 있습니다)
- 근무표 템플릿 저장/불러오기 (지난주 복사는 됩니다)
- 단말 무응답 알림의 외부 발송 (화면에는 표시됩니다)

## 운영 시 주의

- **HTTPS 뒤에 두세요.** HTTP 로만 접근하는 내부망이면 `COOKIE_SECURE=false` 로
  두어야 합니다 — 아니면 로그인이 조용히 무한 반복됩니다.
- **국내 리전을 쓰세요.** 해외 리전은 국외이전 고지·동의 절차가 붙습니다.
- **복구를 실제로 해보세요.** 해본 적 없는 백업은 백업이 아닙니다.
  `pg_dump -n store_gangnam` 으로 매장 하나만 떼어낼 수 있습니다.
