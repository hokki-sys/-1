# 온라인 소매가 추적 시스템 설계 (네이버 · 쿠팡)

민물장어 가공품(필렛·양념 등)의 온라인 소매가를 자동 추적하기 위한 설계서.
코드는 포함하지 않으며, 무엇을 어떤 구조로 만들지만 정한다.

- 작성일: 2026-08-25
- 대상 저장소: `hokki-sys/-1` (기존 `tracker/` 확장)
- 범위: 네이버 · 쿠팡 2개 포털

---

## 0. 한 줄 결론

> **"판매글(오퍼)"을 데이터의 최소 단위로 삼고, 키워드 전수 스캔 대신
> 고정 패널(대표 판매글 묶음)을 매일 관측한다. 여러 판매자 문제는
> `추적품목 1 : N 오퍼` 관계로 풀고, 비교는 반드시 `원/kg` 환산값으로 한다.**

두 가지가 이 설계의 축입니다.

1. **여러 판매자 문제** → 3계층 모델(품목 / 오퍼 / 스냅샷)로 해결. 5장·6장.
2. **네이버 쇼핑 검색 API 종료** → 수집 방식을 "검색"에서 "패널"로 전환. 4장·8장.

두 번째는 질문하신 내용은 아니지만, 이걸 모르고 설계하면 1~2주 작업이
그대로 버려집니다. 그래서 먼저 다룹니다.

### 막힌 지점

**네이버 쇼핑 검색 API가 2026-07-31 종료되었고 공식 대체제가 없습니다.**
`market_price.py`가 비활성인 이유이며, 등록해두신 `NAVER_CLIENT_ID` /
`NAVER_CLIENT_SECRET`는 현재 무용지물입니다.

포털별로 지금 실제로 열려 있는 경로는 다음과 같습니다.

| 채널 | 얻는 것 | 현재 가용성 | 판정 |
|---|---|---|---|
| 네이버 쇼핑 검색 API | 키워드 → 상위 100건 최저가 | ❌ **종료(2026-07-31)** | 사용 불가 |
| 네이버 데이터랩 쇼핑인사이트 | 카테고리·키워드 클릭 트렌드 | ✅ (API HUB 이관) | 가격 없음 → **수요 신호로만** |
| 네이버 커머스API | 스마트스토어 **자사** 상품 | ✅ 자사 스토어 보유 시 | 내 가격 전용 |
| 네이버 상품 URL 직접 조회 | 특정 판매글 가격 | ⚠️ `robots.txt`·약관 확인 필요 | **주력 후보** |
| 쿠팡 파트너스 오픈API | 키워드 → 상품 검색 | ⚠️ 승인 필요 + **시간당 10회 / 회당 10건** | 발견용으로만 |
| 쿠팡 상품 URL 직접 조회 | 특정 판매글 가격 | ⚠️ 봇 차단 강함 | **주력 후보(난이도 상)** |
| 유료 데이터 제공사 | 키워드 → 정규화된 가격비교 데이터 | 💰 유료 | 예산 있으면 최선 |

**설계에 미치는 영향:** "매일 키워드로 상위 100개를 긁어 시세를 만든다"는
원래 접근은 두 포털 모두에서 불가능하거나 비경제적입니다. 대신
**대표 판매글을 고정해두고 그것만 매일 보는 방식**으로 전환해야 합니다.

이건 차선책이 아니라 오히려 정석입니다. 소비자물가지수(CPI)도 시장의
모든 가격을 세지 않고 **대표 품목 바스켓을 고정해 추적**합니다. 매일 다른
상위 100개를 보면 순위 변동이 가격 변동으로 오인되는 노이즈가 끼지만,
같은 판매글을 계속 보면 **진짜 가격 변화만** 잡힙니다.

## 2. 설계 원칙

이후 모든 결정은 이 세 가지에서 파생됩니다.

**원칙 1 — 관측 사실과 해석을 분리한다.**
"○○수산 상품페이지에서 오늘 29,600원을 봤다"는 **사실**이고,
"민물장어 필렛 시세는 kg당 58,000원이다"는 **해석**입니다.
사실은 추가만 하고 절대 수정하지 않으며(append-only), 해석은 언제든
전부 다시 계산할 수 있는 파생물로 둡니다.

> 왜 중요한가: 나중에 "이 판매글을 잘못 분류했다"를 발견해도, 분류만
> 고치고 재계산하면 과거 이력이 전부 복구됩니다. 반대로 집계값만
> 저장해두면 그날로 데이터가 죽습니다.

**원칙 2 — 비교는 정규화된 값으로만 한다.**
표시가격끼리는 절대 비교하지 않습니다. 규격이 다르기 때문입니다.
비교 단위는 **배송비 포함 원/kg**으로 통일합니다.

**원칙 3 — 판별은 사람, 계산은 기계.**
"이 두 판매글이 같은 제품인가"는 자동화 난이도가 높고 틀리면 지표가
통째로 오염됩니다. 패널 규모가 수십 개 수준이라면 **사람이 한 번 확정**하고,
기계는 수집·환산·집계·알림만 맡는 게 정확도와 공수 양쪽에서 유리합니다.

## 4. 데이터 모델 — "여러 판매자" 문제의 답

질문의 핵심입니다. **3계층으로 나누면 깔끔하게 풀립니다.**

```
① 추적품목 (item)          내가 "시세를 알고 싶은 개념"
   예) 민물장어 필렛 · 냉동 · 국내산
        │
        │ 1 : N          ← 여기가 "여러 판매자"를 흡수하는 지점
        ↓
② 오퍼 (offer)            판매자 × 상품페이지 × 옵션 = 가격의 최소 단위
   예) 쿠팡 / ○○수산 / 민물장어필렛 500g×2 / 로켓프레시
   예) 네이버 / △△푸드 / 손질장어 필렛 1kg / 기본옵션
        │
        │ 1 : N (시간)
        ↓
③ 스냅샷 (snapshot)        하루 한 번의 관측 기록 (추가 전용)
   예) 2026-08-25 / 32,900원 / 배송비 0 / 원/kg 32,900 / 재고있음
```

### 왜 오퍼가 최소 단위여야 하는가

같은 제품이라도 판매자마다 **가격·배송비·옵션 구성·재고**가 전부 다릅니다.
품목 단위로만 저장하면 "오늘 최저가 32,900원"만 남고, 그게 **누가 내렸는지**,
**한 명이 던진 건지 시장 전체가 내린 건지** 알 수 없습니다. 오퍼 단위로
쌓으면 나중에 어떤 묶음으로든 다시 집계할 수 있습니다.

추가 이점: **매칭 오류의 비용이 낮아집니다.** 오퍼를 잘못 분류했어도
`item_id` 한 칸만 고치면 과거 스냅샷이 그대로 올바른 품목으로 재집계됩니다.
매칭과 관측이 한 덩어리면 재수집 말고는 방법이 없습니다.

### 옵션을 오퍼로 쪼개는 이유

네이버·쿠팡 모두 한 상품페이지 안에 여러 옵션(500g / 1kg / 2kg)이 있고
**옵션마다 가격이 다릅니다.** 페이지 단위로 다루면 "이 페이지의 가격"이
정의되지 않습니다. `(상품페이지, 옵션)` 조합을 오퍼로 잡아야 가격이
하나로 확정됩니다.

> 실무 함정: 검색 결과나 페이지 상단에 표시되는 대표가격은 대개
> **최저 옵션가**입니다. "1kg 45,000원"으로 보이는 상품이 실제로는
> 500g 옵션 가격인 경우가 흔합니다. 옵션을 명시적으로 고정해야
> 이 함정을 피합니다.

### 품목(item) 정의는 어떻게 자를 것인가

장어는 규격 축이 여럿이라 이 결정이 지표 품질을 좌우합니다. 권장 축:

| 축 | 값 예시 | 비교 그룹 분리 필요성 |
|---|---|---|
| **형태** | 필렛 / 양념구이 / 통장어 / 장어탕 | **필수** — 양념은 소스 무게가 포함돼 필렛과 원/kg 직접 비교 불가 |
| **원산지** | 국내산 / 중국산 / 일본산 | **필수** — 가격대가 근본적으로 다름 |
| **보관** | 냉동 / 냉장 / 활 | 필수 |
| **미수(마리 수)** | 1kg당 6미 / 8미 / 10미 | **권장** — 장어는 마리당 크기가 품질·가격의 핵심 변수 |
| 중량 | 500g / 1kg / 2kg | 불필요 — 원/kg 환산으로 흡수 |

즉 **중량은 정규화로 흡수하고, 형태·원산지·보관·미수는 품목을 나눕니다.**
처음부터 미수까지 쪼개면 품목당 오퍼가 너무 적어지니, 1단계에서는
`형태 × 원산지 × 보관`으로 시작하고 데이터가 쌓이면 미수를 분리하는
쪽을 권합니다.

## 5. 동일 상품 판별 (매칭) 설계

"같은 제품을 여러 판매자가 판다"를 실제로 판별하는 절차입니다.
**4단 사다리로 두고, 위에서부터 적용하되 아래가 항상 위를 이깁니다.**

```
L3  사람 확정 (override)      ← 최우선. 한 번 정하면 영구 적용
     ↑
L2  검토 큐 (pending)         ← 자동 판별 신뢰도 낮음 → 사람에게 넘김
     ↑
L1  규격 정규화 키             ← 제목 파싱으로 자동 그룹핑
     ↑
L0  포털 자체 그룹핑           ← 있으면 공짜로 사용
```

### L0 — 포털이 이미 묶어준 것

- **쿠팡**: 같은 상품페이지(`productId`) 아래 여러 판매자 아이템(`vendorItem`)이
  달립니다. 같은 `productId`면 사실상 동일 상품으로 간주해도 안전합니다.
- **네이버**: 가격비교 카탈로그로 묶인 상품군이 있습니다. 다만 검색 API
  종료로 카탈로그 ID를 프로그램으로 받아올 수 없어, **패널 등록 시 URL에서
  추출해 수기 기록**하는 방식이 됩니다.

장어 가공품은 브랜드 표준화가 약해 카탈로그 매칭률이 낮습니다.
**L0에 기대하지 말고 L1~L3를 주력으로 보세요.**

### L1 — 규격 정규화 키

상품명에서 속성을 뽑아 정규화 키를 만듭니다.

```
"[산지직송] 국내산 손질 민물장어 필렛 500g x 2팩 (냉동) 8미"
        ↓ 파싱
{ 형태: 필렛, 원산지: 국내산, 보관: 냉동, 총중량: 1000g, 미수: 8 }
        ↓ 키 생성
"필렛|국내산|냉동"   → item_id 후보
```

파싱 대상과 기존 자산 활용:

| 속성 | 추출 방법 | 현재 상태 |
|---|---|---|
| 총중량 | `1kg`, `500g x 2`, `500그램` → g 환산 | ✅ `parse_weight_g()` 구현됨. 이중계산 방지까지 처리 |
| 어종 필터 | 붕장어·바다장어·아나고·꼼장어, 진액·소스류 제외 | ✅ `EXCLUDE_TERMS` 구현됨 |
| 형태 | 필렛/필레, 양념/데리야끼, 통/장어탕 | 🔧 신규 |
| 원산지 | 국내산/국산, 중국산, 일본산 | 🔧 신규 |
| 보관 | 냉동/냉장/활 | 🔧 신규 |
| 미수 | `8미`, `8마리`, `1kg 8미` | 🔧 신규 |

### L2 — 검토 큐

자동 판별이 애매하면 **틀린 답을 내지 말고 보류**합니다.
`panel_offers.csv`의 `match_status`를 `pending`으로 두고, 그 오퍼는
집계에서 제외한 채 스냅샷만 계속 쌓습니다. 일일 리포트 하단에
"확인 필요 N건"으로 노출해 사람이 처리하게 합니다.

보류 조건: 중량 파싱 실패 / 형태·원산지 미검출 / 원/kg가 기존 분포의
IQR을 크게 벗어남.

### L3 — 사람 확정

사람이 `item_id`를 직접 적으면 `match_status=confirmed`가 되고
**이후 자동 로직은 이 오퍼를 건드리지 않습니다.**

> **핵심 권고:** 자동 매칭 정확도 100%를 목표로 삼지 마세요.
> 패널이 30~80개 오퍼 규모라면 초기 확정에 1~2시간, 이후 월 10~20분이면
> 충분합니다. 그 시간을 아끼려고 매칭 엔진을 만들면 훨씬 큰 비용이 들고,
> 조용히 틀린 지표가 나옵니다. **자동화할 것은 판별이 아니라 수집·환산·알림입니다.**

## 6. 가격 정규화

### 6-1. 어떤 가격을 기록할 것인가

표시가 하나만 저장하면 나중에 되돌릴 수 없습니다. **분리해서 전부 저장**합니다.

| 필드 | 의미 | 비고 |
|---|---|---|
| `list_price` | 정가 / 할인 전 가격 | 없으면 비움 |
| `sale_price` | 실제 판매가 | 주 관측값 |
| `coupon_price` | 즉시할인·카드쿠폰 적용가 | 확인 가능할 때만 |
| `shipping_fee` | 배송비 | 무료면 0, **미확인이면 비움(0 아님)** |
| **`total_price`** | `sale_price + shipping_fee` | **비교 기준값** |
| `is_rocket` / `is_free_ship` | 로켓배송·무료배송 플래그 | 별도 보관 |

**`0`과 `빈 값`을 절대 섞지 마세요.** "배송비 0원"과 "배송비 확인 못 함"은
완전히 다른 사실이고, 이걸 혼동하면 시세가 조용히 왜곡됩니다.

### 6-2. 단위 환산

```
won_per_kg = total_price ÷ (total_g ÷ 1000)
```

미수가 파악되면 `won_per_ea`(마리당 가격)도 함께 계산합니다. 장어는
"kg당 얼마"보다 "8미 기준 마리당 얼마"가 현장 감각에 가까운 경우가 많습니다.

**양념 제품 주의:** 양념구이는 소스·양념 무게가 총중량에 포함되어
같은 원/kg이라도 실제 장어 함량은 다릅니다. **양념과 필렛은 반드시 다른
품목으로 분리**하고, 굳이 비교해야 한다면 별도 환산계수를 두되 그 계수는
추정치임을 명시하세요.

### 6-3. 이상치 처리

제외 대상: 100g 미만 샘플, 세트·선물세트, 사은품 끼워팔기, 비정상 저가.

판정 규칙(초기값, 데이터 쌓이면 조정):

- 총중량 밴드: 300g ~ 5,000g 밖이면 제외
- 원/kg 밴드: 품목별 직전 30일 중앙값의 0.4배 ~ 2.5배 밖이면 보류
- 절대가 밴드: 5,000원 ~ 1,000,000원 (기존 `keep_listing` 로직 계승)

> **제외해도 스냅샷은 반드시 남깁니다.** 통계에서만 빼고 기록은 유지합니다.
> 기존 `market_price.py`가 이미 이 원칙을 지키고 있으니 그대로 계승합니다.
> 나중에 "그때 그 이상한 가격이 뭐였지"를 역추적할 수 있어야 합니다.

## 7. 수집 설계

### 7-1. 패널 방식

키워드 스캔이 아니라 **고정된 오퍼 목록을 매일 순회**합니다.

- 규모: 품목당 오퍼 8~15개, 전체 **30~80개** 권장
  - 8개 미만이면 중앙값이 불안정하고, 100개 넘으면 관리 비용이 급증합니다.
- 구성: 포털별로 균형 있게, 상위 노출 판매자 위주 + 주요 경쟁사 필수 포함
- 실행: 하루 1회, 기존 07:30 KST 배치에 합류

요청량은 **하루 30~80건**으로 매우 가볍습니다. 두 포털 어느 쪽에도
부담을 주지 않는 수준이며, 이게 이 방식의 실무적 강점입니다.

### 7-2. 수집 시 지켜야 할 것

`track_price.py`에 이미 구현된 원칙을 그대로 확장 적용합니다.

- **`robots.txt` 우선 확인** — 금지 경로는 건너뛰고 `robots_blocked` 상태로 기록
  (이미 구현돼 있음: `robots_allowed()`)
- 요청 간 지연·지터, 실패 시 지수 백오프
- 신원 밝히는 User-Agent 유지
- 하루 1회 고정 시각 — 잦은 재시도 금지
- 로그인·결제 뒤 가격은 수집 대상에서 제외

쿠팡은 봇 탐지가 강해 URL 직접 조회가 차단될 수 있습니다.
**차단 시 우회 시도는 하지 말고**, 해당 오퍼를 `blocked`로 표시한 뒤
파트너스 API 또는 수기 갱신으로 전환하는 게 맞습니다.

### 7-3. 실패 상태 구분

한 칸에 뭉뚱그리면 나중에 원인 분석이 불가능합니다. **상태를 분리**합니다.

| 상태 | 의미 | 집계 처리 |
|---|---|---|
| `ok` | 정상 수집 | 포함 |
| `out_of_stock` | 페이지 살아있음 / 품절 | 제외하되 **판매자 수에는 반영** |
| `not_found` | 페이지 삭제·판매 종료 | 오퍼 `dead` 전환 후보 |
| `robots_blocked` | robots.txt 금지 | 영구 제외 |
| `blocked` | 봇 차단·접근 거부 | 재시도 대상 |
| `parse_failed` | 페이지는 받았으나 가격 못 찾음 | **운영 알림 대상(구조 변경 신호)** |

`parse_failed`가 갑자기 늘면 사이트 구조가 바뀐 것입니다. 이걸 별도로
잡아내는 게 트래커 수명을 결정합니다.

## 8. 패널 갱신 (신규 판매자 발견)

고정 패널의 유일한 약점은 **새로 진입한 판매자를 놓친다**는 점입니다.
주기적 갱신으로 보완합니다.

- **주기**: 월 1회 (계절성 큰 시기엔 격주)
- **발견 경로**:
  1. 쿠팡 파트너스 API 키워드 검색 — 승인 시. 단 **시간당 10회 / 회당 10건**
     제한이라 발견 용도로만 쓰고 일상 수집에는 쓰지 않습니다.
  2. 네이버 — 사람이 직접 검색해 URL 추가 (API 부재로 자동화 불가)
  3. 유료 데이터 제공사 — 예산 확보 시 1·2를 대체
- **기록**: `panel_changelog.csv`에 진입/이탈 이력을 남깁니다.

> 부수 효과: **판매자 진입·이탈 자체가 시장 신호입니다.** "이번 달 신규
> 3곳 진입, 2곳 이탈"은 가격 못지않게 중요한 정보이므로 리포트에 포함합니다.

### 지수 연속성 주의

패널을 바꾸면 그날 시세가 점프한 것처럼 보입니다. 실제 가격 변동이 아니라
관측 대상이 바뀐 것입니다. 처리 방법:

- 최소한: 리포트에 **"패널 변경일"을 표시**해 해석 시 감안하게 함
- 권장: 변경 당일 **구/신 패널을 모두 관측**해 비율로 이어붙임(체인 링크)

## 9. 파일 스키마

기존 CSV + GitHub 커밋 방식을 유지합니다. 이 규모에는 DB가 과합니다.

```
tracker/
  panel_items.csv        추적품목 정의        (사람이 관리)
  panel_offers.csv       오퍼 정의            (사람 + 반자동)
  offer_snapshots.csv    일별 관측 기록        ★ append-only, 수정 금지
  item_daily.csv         품목 일별 집계        ◇ 파생물, 언제든 재생성
  panel_changelog.csv    패널 변경 이력        (사람이 관리)
```

### panel_items.csv — 추적품목

```
item_id, label, form, origin, storage, size_grade, compare_group, active, note
```
- `compare_group`: 서로 비교 가능한 품목 묶음 (예: 필렛끼리)
- `size_grade`: 미수 등급. 1단계에서는 비워둠

### panel_offers.csv — 오퍼 (여러 판매자를 담는 표)

```
offer_id, item_id, portal, seller_name, url, option_label,
external_id, catalog_id, total_g, unit_count,
match_status, match_method, added_on, status, note
```
- `match_status`: `confirmed` | `auto` | `pending`
- `status`: `active` | `dead` | `blocked`
- `total_g`: 자동 파싱값을 사람이 검증해 확정. **확정되면 자동 갱신 금지**

### offer_snapshots.csv — 관측 사실 (★ 핵심)

```
date, offer_id, status, title,
list_price, sale_price, coupon_price, shipping_fee, total_price,
total_g, won_per_kg, won_per_ea,
stock, is_rocket, is_free_ship, outlier_flag, source, url
```
- **추가만 하고 절대 수정하지 않습니다.**
- `outlier_flag`가 있어도 행은 남깁니다. 집계에서만 제외합니다.
- `source`: 가격을 어느 위치에서 뽑았는지 (기존 `id:realPrc` 같은 표기 계승)

### item_daily.csv — 파생 집계

```
date, item_id, n_offers, n_sellers, n_in_stock,
min_won_per_kg, p25_won_per_kg, median_won_per_kg, p75_won_per_kg,
min_total_price, spread_ratio, d1_pct, d7_pct, d30_pct, is_30d_low
```
- **스냅샷만 있으면 전부 재생성 가능해야 합니다.** 이게 원칙 1의 실체입니다.
- `spread_ratio` = `max ÷ min`. 판매자 간 가격 분산 = 경쟁 강도 지표.

### 용량 검토

오퍼 80개 × 365일 = 연 **29,200행**. CSV로 5년 이상 무리 없습니다.
그 이후 또는 시간당 수집으로 전환할 때 SQLite로 옮기면 됩니다.
지금 DB를 도입할 이유는 없습니다.

## 10. 집계 지표

**중앙값을 대표값으로 씁니다.** 평균은 이상치 하나에 흔들립니다.

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| `median_won_per_kg` | 품목 내 중앙값 | **대표 시세** |
| `min_won_per_kg` | 최저가 | 공격적 가격 하한 |
| `p25` / `p75` | 사분위 | 정상 가격대 폭 |
| `n_sellers` | 활성 판매자 수 | 경쟁 밀도 |
| `spread_ratio` | 최고÷최저 | 값이 크면 시장 미성숙 or 품질 편차 |
| `is_30d_low` | 30일 최저 경신 | 하락 국면 진입 신호 |

### 교차 분석 — 이 시스템의 진짜 가치

이미 **도매 경매가**(`wonmul_history.csv`)와 **수입 단가**(`import_history.csv`,
`japan_import_history.csv`)를 쌓고 계십니다. 소매가가 붙으면
**수입단가 → 도매가 → 소매가** 전 구간이 한 화면에 들어옵니다.

- `retail_median ÷ wholesale_median` = **유통 마진율 추이**
- 수입단가 상승이 소매가에 반영되기까지의 **시차(lag)**
- 마진율이 평소 대비 벌어지는 시점 = **매입 또는 가격 조정 타이밍**

원가 근거 자료로서 도매·수입 단독보다 설득력이 훨씬 큽니다.
`daily_report.py`가 이미 다기간 비교 틀을 갖고 있어 섹션 추가로 구현됩니다.

## 11. 알림 설계

기존 GitHub 이슈 + Slack/메일 경로를 그대로 씁니다.

| 이벤트 | 조건(초기값) | 등급 |
|---|---|---|
| 시세 급변 | 품목 중앙값 원/kg 전일 대비 ±5% | 높음 |
| 최저가 경신 | 30일 최저 하회 | 높음 |
| 신규 진입 | 새 판매자 오퍼 등장 | 보통 |
| 판매자 이탈 | `not_found` 7일 지속 | 보통 |
| 품절 확산 | 품목 내 품절 비율 30% 초과 | 보통 |
| **수집 이상** | `parse_failed` 비율 20% 초과 | **높음(운영)** |
| 검토 필요 | `pending` 오퍼 5건 이상 누적 | 낮음 |

### 노이즈 억제 — 이게 없으면 알림을 곧 무시하게 됩니다

- **2회 연속 확인 후 발송**: 하루치 튐으로는 알리지 않음
- **동일 이벤트 쿨다운 7일**: 같은 사유 반복 발송 금지
- **일일 리포트는 변동 없어도 발송** (현재 정책 유지 — 침묵과 장애 구분)
- 급보성 알림만 이슈 생성, 나머지는 리포트 본문에 요약

`parse_failed` 알림을 "운영 등급 높음"에 둔 게 핵심입니다. 가격 변동
알림은 안 와도 손해가 제한적이지만, **수집이 조용히 죽으면 시스템 전체가
무의미해집니다.**

## 12. 운영 가드레일

| 위험 | 증상 | 대비 |
|---|---|---|
| 사이트 구조 변경 | `parse_failed` 급증 | 파싱 성공률 모니터링 + 알림. 원본 HTML 스냅샷 보관(이미 `.debug/` 구현됨) |
| 봇 차단 | `blocked` 발생 | 우회 시도 금지. 오퍼 상태 전환 후 대체 경로 확보 |
| 매칭 오염 | 시세가 갑자기 튐 | `pending` 격리 + 이상치 밴드 + 사람 검토 큐 |
| 옵션 함정 | 실제보다 싸게 기록 | 오퍼에 옵션 고정, `total_g`는 사람이 확정 |
| 패널 노후화 | 실제 시장과 괴리 | 월 1회 갱신 + `changelog` 기록 |
| 데이터 소실 | — | 스냅샷 append-only, Git 이력이 곧 백업 |

**약관·법적 고려:** 두 포털 모두 자동 수집에 제약이 있습니다.
`robots.txt` 준수, 하루 1회 저빈도, 공개 페이지만, 로그인 우회 없음,
수집 데이터는 사내 분석 목적으로만 사용 — 이 선을 지키는 설계입니다.
상업적 재배포나 대량 수집으로 확장할 계획이라면 **유료 데이터 제공사
계약이 정답**입니다.

운영하면서 임계값을 조정하는 성격입니다.

## 14. 결정이 필요한 사항

설계를 구현으로 옮기기 전에 아래가 정해져야 합니다.
지금은 **A안을 기본 가정**으로 두고 작성했습니다.

1. **자사 판매 여부** — 네이버 스마트스토어·쿠팡에서 직접 판매 중인가?
   - A(가정): 아니오 → 시장 시세 관측이 목적. 지표는 중앙값 중심
   - B: 예 → 커머스API로 내 가격을 붙이고 **가격 순위·역전 알림**이 주력이 됨

2. **주 용도** — 지표 우선순위가 갈립니다.
   - A(가정): 매입·판매가 결정의 근거 자료 → 중앙값·마진율 중심
   - B: 경쟁사 감시 → 특정 판매자 지목 추적·즉시 알림 중심

3. **패널 규모** — 30개(가볍게 시작) vs 80개(대표성 확보)

4. **예산** — 유료 데이터 제공사를 쓸 수 있는가?
   쓸 수 있다면 네이버 API 종료 제약이 사라지고 키워드 전수 스캔이
   다시 가능해져, 8장의 패널 갱신 부담이 크게 줄어듭니다.

5. **품목 정의** — 실제로 추적할 3~5개를 확정해야 합니다.
   초안: `필렛·국내산·냉동` / `필렛·중국산·냉동` / `양념구이·냉동` /
   `통장어·냉동`
